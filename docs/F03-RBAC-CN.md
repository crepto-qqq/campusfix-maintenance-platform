# F03 — 多角色账号与活动角色

## 角色与身份

公开注册只创建 `STUDENT` 身份及 `GENERAL_USER` 角色。`STUDENT` 是校园身份，`GENERAL_USER` 才是用于授权的学生／报修人角色。用户不能通过注册或个人资料接口授予自己高级权限。

一个账号可以持有多个有效角色，但每个浏览器标签页同一时间只以**一个活动角色**使用工作区：

| 活动角色 | 工作区权限 |
|---|---|
| `GENERAL_USER`（Student / Requester） | 提交报修，查看自己的工单；只能编辑或取消自己尚未分配的 `SUBMITTED` 工单；评价本人已完成工单、浏览公开评价及举报评论 |
| `MAINTENANCE_STAFF` | 查看有效分配给自己的工单；只能更新自己当前被分配的维修任务；仅查看本人的平均评分 |
| `ADMINISTRATOR` | 查看全部工单，管理优先级、分配及用户角色；查看完整评价、审核举报和管理学生评价封禁 |

**权限不取并集。**例如持有 `GENERAL_USER` 和 `MAINTENANCE_STAFF` 的人，以学生角色进入时只看到本人报修和学生操作；切换到维修人员后只看到分配任务和维修操作。即使同一工单由本人提交且分配给本人，页面和接口也只按当前活动角色处理。管理员若同时持有其他角色，需要切换后才能执行相应操作。

评价也按活动角色隔离：维修模式不能取得逐条评分、评论或作者；兼有学生／管理员角色的账号切换后可按对应模式查看。无论切换到什么角色，同一人不能给自己完成的工单评分；管理员不能处理自己写的评价、自己提交的举报或解除自己的评价封禁。具体规则见 [维修人员评分、评价与审核](Technician-Ratings-Reviews-CN.md)。

`MANAGER` 不再是可选的活动角色或可授予的新角色。已有仅持有 `MANAGER` 的账号迁移为 `GENERAL_USER`；同时持有 `MANAGER` 与上述角色的账号保留上述角色，并移除 `MANAGER` 授权。历史记录仍保留。

## 登录、切换与授权

登录仍使用邮箱与密码。单角色账号直接以该角色进入 Dashboard；多角色账号在进入 Dashboard 前选择一个已授予的角色。Dashboard 提供角色切换器，切换后导航、徽标、统计、工单列表和详情操作都立即按新活动角色刷新。工作区左下角只显示当前活动角色；个人资料可展示账号持有的全部角色。

`POST /api/auth/active-role` 接收 `{"role":"GENERAL_USER"}` 等受支持角色并检查当前账号是否持有。未登录返回 `401`；选择未授予或不受支持的角色返回 `403`。角色选择不改变账号授权，也不写入服务器 Session。浏览器每个标签页保存各自的活动角色，在受保护请求中传 `X-Active-Role`；图片请求使用 `activeRole` 查询参数。两个标签页可以同时使用不同角色，互不切换。若另一个标签页登录了不同账号或登出，原标签页会清除旧角色并离开旧工作区；获得焦点时还会重新核对当前账号。

后端从数据库重新读取账号的有效角色，并按本次请求的活动角色授权。多角色账号对其他受保护接口缺少或使用无效活动角色时返回 `409`，要求重新选择；`GET /api/users/me` 会返回 `activeRole: null` 供界面恢复角色选择。单角色账号没有请求头时自动使用唯一角色；撤权后若继续携带旧角色请求头，受保护接口返回 `409`，而 `/api/users/me` 返回唯一剩余角色供界面恢复。撤权对后续请求立即生效；禁用账号不能继续使用已有会话。

## 存储与兼容

沿用 `system_roles` 与 `user_role_assignments`，无需删除本地数据库。增加角色保留其他有效角色；撤销角色保留原记录并填写撤销时间；重复保存不会生成重复授权记录。

注册、登录、个人资料和管理员列表保留 `roles` 数组。登录与当前用户响应还提供 `activeRole`。旧 `role` 字段仅供旧客户端显示，不能替代活动角色进行授权。

## 管理员接口

`GET /api/admin/users` 返回用户资料和已授予角色集合，但只有当前活动角色为 `ADMINISTRATOR` 的用户可以访问。

`PUT /api/admin/users/{userId}` 接收完整的目标角色集合：

```json
{
  "identityType": "CAMPUS_STAFF",
  "roles": ["GENERAL_USER", "MAINTENANCE_STAFF"]
}
```

保留集合中的已有角色、增加新选角色、撤销未选角色。至少保留一个受支持角色；空集合、`null` 元素、未知或退役角色，以及同时传入 `role` 和 `roles` 均返回 `400`。为兼容旧客户端，仍接受 `identityType` + 单个 `role`，以及旧 `PUT /api/admin/users/{userId}/role`；这两种请求表示替换为一个角色。

未登录返回 `401`，非管理员活动角色返回 `403`，撤销最后一个管理员角色返回 `409`。角色更新使用事务锁，防止并发撤权导致系统没有管理员。

## 验证

在 `backend` 目录运行 `./gradlew test`（Windows 使用 `.\gradlew.bat test`，Java 21）。测试使用独立内存数据库，不修改本地数据。在项目根目录运行 `node --test frontend/tests/multiple-roles.test.cjs`。前端单元测试不能替代真实浏览器布局验收。

自动化重点：多角色登录前选择、Dashboard 切换、单角色页面可见性、本人／分配／全部工单隔离、不可跨角色操作、未授予角色拒绝、撤权即时生效、同账号不同标签页或客户端独立活动角色，以及管理员授权历史与最后管理员保护。

手动验收：

1. 管理员为测试账号授予 `GENERAL_USER` 与 `MAINTENANCE_STAFF`；准备一张该账号提交的工单，以及另一人提交但分配给该账号的工单。
2. 测试账号登录时选 Student，进入 Dashboard 后确认左下角只有 Student，只有本人报修和学生操作；另一张分配工单及维修按钮不可见。
3. 在 Dashboard 切换 Maintenance Staff，确认左下角、导航、统计与列表均切换；只显示当前分配任务及对应维修操作。刷新和进入详情页后仍保持该模式。
4. 用另一个标签页选择不同角色，确认两个标签页可以各自工作，切换一边不会改变另一边。
5. 管理员撤销该账号的维修角色后，旧标签页的后续维修请求立即失效，页面回到有效角色。尝试选择未授予或退役角色应被拒绝。
6. 尝试撤销最后一个管理员的 `ADMINISTRATOR`，应返回 `409`。
